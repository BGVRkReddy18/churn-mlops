What makes it different

Not just a model in a notebook

Most churn projects stop at a trained model and an accuracy score. This one treats the model as a production system, then asks a research question that most MLOps tutorials never test.

ConcernTypical student projectThis project
WorkflowOne Jupyter notebook run by handDVC 4-stage pipeline (ingest → validate → train → evaluate). Every parameter lives in params.yaml, and only stages that changed re-run.
Data qualityAssumes the CSV is cleanSchema validation that fails fast on bad data, plus one schema.py shared by training and the API, so there is no train/serve skew.
TrainingDefault hyperparameters, threshold 0.5Optuna search with 5-fold CV over 3 model families. The decision threshold is tuned on out-of-fold predictions, so the test set never leaks.
TrackingResults copied into a reportMLflow logs every trial and stores the model in a registry. A quality gate blocks weak models, and only a model at least as good as the current one becomes @champion.

AutomationNoneGitHub Actions runs lint, 40+ tests, retraining, a Docker smoke test and a registry push, then deploys this site automatically.
ResearchNoneA controlled study with statistical tests (Friedman, Nemenyi, Wilcoxon-Holm): do drift alarms really tell you when to retrain?
01 · RIGOUR

Experiments, not anecdotes

7 detectors × 10 retraining policies × 9 drift scenarios, each repeated 50 times on new data splits and models, then validated on a real dataset with natural drift.

02 · A SURPRISING FINDING

Standard practice can backfire

Retraining whenever input drift is detected (the common MLOps default) made the churn model worse than never retraining.

03 · APPLIED BACK

Findings shape the system

The research directly informs this system's monitoring design: PSI as a data-quality alarm, retraining gated on measured performance, and a promotion gate.

Research study

When should a production model be retrained?

MLOps tools usually alert, or retrain automatically, when the input data drifts. We tested that chain of assumptions under controlled drift on this churn model, with every detector calibrated to the same 1% false-alarm rate.

What drift monitors detect ≠ what hurts the model

Damage to the model compared with how often the industry-standard PSI monitor raised an alarm (50 runs per scenario).

model damage (ROC-AUC lost)PSI detection rate
−0.33 AUCConcept drift is invisible to input monitors

When customer behaviour changes but their profile doesn't, the model drops to coin-flip accuracy and PSI, KS, MMD and the classifier test all stay silent.

Worse than staticRetraining on input-drift alarms backfired

It reacted to harmless shifts and threw away training data. Triggering on a measured drop in AUC matched a perfectly timed oracle with 77% fewer retrains than a fixed schedule.

−64% retrainsOn real drift, the right trigger saves cost

On the Elec2 electricity market data, a calibrated KS-test trigger was statistically tied with retraining every week (p = 0.59) while retraining 64% less often.
